# 能力注册中心设计方案（参考 Nacos AP/CP 模式）

> 目标：让**其他项目的业务能力**注册到 CosyAgent 后端，Agent 在 ReAct 循环中像调用本地工具一样调用远程能力。
> 参考 Nacos 注册中心的双模式设计：**AP（临时实例 / 可用性优先 / 最终一致）** 与 **CP（持久实例 / 强一致 / 故障选主）**，
> 按能力场景选择一致性模型。

---

## 1. 背景与现状

| 现状 | 局限 |
| --- | --- |
| 工具 = 本地 `AgentTool` Bean（ServerTimeTool / ServerInfoTool），启动时注入 `ToolRegistry` | 工具与后端进程强绑定，新能力必须改 CosyAgent 代码、重新发版 |
| 模型通过 `AgentToolBridging` 看到工具定义（JSON Schema FunctionTool） | 外部项目无法自助接入，Agent 能力被锁定在单体进程内 |

**设计目标**：
1. 外部项目**零改动接入**：声明能力（名称/描述/参数 Schema + HTTP 端点）即可被 Agent 使用
2. **AP / CP 双模式**：动态服务走 AP（心跳续约、超时摘除），固定服务走 CP（持久化、强一致、不因心跳丢失摘除）
3. 与现有 ReAct 循环、容错（ResilienceTarget.TOOL）、统一协议（Result）无缝集成
4. 注册中心本身无状态化演进：单机先行，多节点可扩展

## 2. 总体架构

```
                    ┌───────────────────────────── CosyAgent ─────────────────────────────┐
                    │                                                                      │
 外部项目(能力提供者) │   agent.capability（新增模块）                                        │
 ┌──────────────┐   │  ┌──────────────────┐    ┌───────────────────┐                        │
 │ Provider A   │───┼─▶│ CapabilityRegistry│──▶│ CapabilityStore    │ (AP: Redis+缓存)      │
 │ (SpringBoot) │   │  │ (注册/心跳/寻址)    │   │                    │ (CP: MySQL 落库)      │
 │ Provider B   │───┼─▶│                   │   │                    │                        │
 │ (云函数/其它) │   │  └────────┬─────────┘   └───────────────────┘                        │
 └──────────────┘   │           │ resolve(name)                                          │
  注册/心跳/调用     │           ▼                                                        │
                    │  ┌─────────────────────┐     ┌─────────────────────┐                │
                    │  │ CapabilityProxyTool  │────▶│ 提供者 HTTP endpoint │                │
                    │  │ (实现 AgentTool)      │     │ (调用时鉴权签名)      │                │
                    │  └─────────┬───────────┘     └─────────────────────┘                │
                    │            │ 注入                                                   │
                    │            ▼                                                        │
                    │  ┌─────────────────────┐     ┌─────────────────────┐                │
                    │  │ ToolRegistry         │────▶│ DefaultReActAgent   │  ReAct 循环     │
                    │  │ (本地工具+远程能力)    │     │ (工具执行/容错/SSE)   │                │
                    │  └─────────────────────┘     └─────────────────────┘                │
                    └──────────────────────────────────────────────────────────────────────┘
```

**一句话链路**：提供者注册能力 → Registry 存续/持久 → `CapabilityProxyTool` 作为普通 `AgentTool` 注入 ToolRegistry → LLM 选中后由 ReAct 循环执行 → Registry 寻址 → HTTP 调用提供者 → 结果回注入 Observation。

## 3. 核心模型

| 概念 | 说明 | 关键字段 |
| --- | --- | --- |
| `CapabilityProvider` | 能力提供者（一个外部项目/服务实例） | providerId、appName、baseUrl、authType、mode(AP/CP)、lastBeatAt、status |
| `Capability` | 能力定义 = Agent 的一个工具 | name（=工具名，全局唯一）、description、parameters(JSON Schema)、endpoint(路径+method)、retryable、version、namespace |
| `CapabilityInstance` | 能力 × 提供者（同能力可多提供者） | capabilityName、providerId、status(UP/DOWN/UNKNOWN)、注册时间、摘除原因 |
| `CapabilityBinding` | 能力名 → 候选实例链（降级顺序） | capabilityName、orderedInstanceIds、activeIndex |

**同能力多提供者**：一个能力名可由多个提供者实例承载（如 `order_query` 由 A/B 两项目同时注册），Registry 维护**候选链**，调用失败按序切换下一实例——与模型路由 `ModelRouter` 的降级语义同构。

## 4. 注册协议（提供者 → CosyAgent，HTTP）

| 接口 | 方法 | 说明 |
| --- | --- | --- |
| `/api/capabilities/register` | POST | 注册能力（声明 mode=AP/CP，返回 instanceId + 调用令牌） |
| `/api/capabilities/beat` | POST | AP 模式心跳续约（携带 instanceId） |
| `/api/capabilities/deregister` | POST | 显式注销（CP 唯一移除途径；AP 也可） |
| `/api/capabilities/{name}/instances` | GET | 查询某能力的所有实例与健康状态 |
| `/api/agent/capabilities` | GET | 管理侧目录（Agent 能力全景 + 健康） |

注册请求体（示例）：

```json
{
  "appName": "order-service",
  "mode": "ap",
  "namespace": "biz",
  "baseUrl": "http://order-service:8080",
  "authType": "shared-secret",
  "capabilities": [
    {
      "name": "query_order",
      "description": "按订单号查询订单状态与金额",
      "parameters": { "orderId": { "type": "string", "description": "订单号" } },
      "endpoint": { "path": "/api/order/query", "method": "POST" },
      "retryable": false
    }
  ]
}
```

响应：`{ instanceId, capabilityNames, callToken }`（callToken 供 CosyAgent 调用提供者时鉴权，仅注册方可见一次）。

## 5. AP / CP 双模式设计（Nacos 对照）

### 5.1 Nacos 机制回顾（设计依据）

| 维度 | AP（临时实例，ephemeral=true） | CP（持久实例，ephemeral=false） |
| --- | --- | --- |
| 协议 | Distro 无主协议 | Raft 选主协议 |
| 写入确认 | 注册即成功（不等待确认） | 需多数派确认 |
| 存储 | 内存（节点各自持有，互相同步） | 磁盘持久化 |
| 存活 | 心跳 5s 续约；15s 超时标记；30s 摘除 | 不因心跳丢失摘除，显式注销才移除 |
| 一致性 | 最终一致（可用性优先） | 强一致（CP 优先） |
| 适用 | 服务发现（动态、弹性扩缩容） | 配置管理（固定、强一致） |

### 5.2 CosyAgent 能力注册映射

| 维度 | AP 模式（临时能力） | CP 模式（持久能力） |
| --- | --- | --- |
| **适用场景** | 动态服务：开发/测试环境、云函数、弹性实例、经常启停的项目 | 固定能力：企业内部网关 API、合规要求强一致、长期稳定的业务系统 |
| **注册语义** | 注册即成功（写入内存态 + Redis，不等待持久确认） | 注册需**落库确认**（MySQL 事务提交成功才返回），返回持久注册号 |
| **存活机制** | 心跳续约：提供者每 5s 调 `/beat`；**15s 未续约 → 标记 SUSPECT；30s 未续约 → 摘除**（与 Nacos 节奏一致） | 不依赖心跳：提供者崩溃不摘除（保活）；仅显式 deregister 或管理 API 移除 |
| **健康检查** | 心跳被动保活 + 调用失败主动摘除（快速失败补偿最终一致） | 主动探测：Registry 定时调提供者 `/healthz`（周期可配）；探测失败标记 DOWN 但**不摘除** |
| **存储** | Redis（instance hash + TTL 自动过期）+ 本地缓存加速读 | MySQL 表 `capability_provider` / `capability`（可复用现有 mysql store 连接参数） |
| **一致性** | 最终一致：允许短暂读到已摘除实例；调用失败快速摘除自愈 | 强一致：注册/注销事务提交后立即全局可见；同名单冲突由唯一约束拒绝 |
| **故障语义** | 服务端/提供者任一故障，已注册能力仍可被读到（可用性优先）；多节点间异步同步（单机先行，后续 Distro 风格扩散） | 提供者故障由健康检查标记 DOWN，调用候选链自动切换；注册中心多节点故障转移需要选主（单机先行，后续 Raft/DB 约束演进） |
| **删除语义** | 超时自动摘除（无需人工） | 必须显式注销（防止误删/漂移） |

### 5.3 模式判定（提供者注册时二选一，也可由管理 API 事后变更）

```
能力是否随实例生命周期启停？ ── 是（动态/弹性）──▶ AP（临时能力）
                          └─ 否（固定/合规/强一致）──▶ CP（持久能力）
```

**默认策略**：注册请求未显式声明 mode 时取配置 `cosy.agent.capability.default-mode`（默认 `ap`，贴近服务发现直觉；生产固定能力显式声明 `cp`）。

## 6. Agent 调用远程能力（执行链路）

```
DefaultReActAgent 工具执行
   → ToolRegistry.find(name)
        ├─ 本地工具：原路径执行（AgentTool）
        └─ 远程能力：CapabilityProxyTool.execute(args)
             → CapabilityRegistry.resolve(name)          // 寻址：AP 读缓存 / CP 直读库
                  → 候选实例链（UP 优先，按注册序）        // 多提供者降级
             → HTTP 调用提供者 endpoint（带 callToken 鉴权 + 超时）
             → 成功：返回结果，续约健康
             → 失败：标记 DOWN → 切下一候选 → 全部失败返回可读错误
```

**复用现有机制**：
- **容错**：远程调用套 `ResilienceSupport.execute(ResilienceTarget.TOOL, ...)`——重试/熔断/限流/超时/舱壁开箱即用；熔断打开返回友好降级文案
- **工具可见性**：`CapabilityProxyTool` 是普通 `AgentTool`，`AgentToolBridging` 自动将其转为 FunctionTool 注入 LLM——**模型无需感知本地/远程差异**
- **SSE 事件**：工具执行事件（tool/toolResult + durationMs）原样生效，客户端渲染无需改动

## 7. 安全设计

| 风险 | 对策 |
| --- | --- |
| 未授权注册 | 注册/心跳接口校验 `X-Capability-Token`（配置 `cosy.agent.capability.token`；为空不启用，与 `cosy.security.api-key` 同机制） |
| 伪造提供者 | 注册返回 `callToken`（仅注册方可见一次）；CosyAgent 调用提供者时携带，提供者校验 |
| 能力名冲突/注入 | 命名空间前缀：能力全名 = `{namespace}_{name}`（namespace 注册时声明）；注册时校验 JSON Schema 合法性、参数/端点白名单规则 |
| 调用方越权 | 管理 API（目录/摘除）走既有鉴权；`enable/disable` 为运维开关 |
| 敏感信息 | callToken / auth 凭据脱敏展示，不入日志（复用 ModelRoutingAdmin 脱敏模式） |

## 8. 存储与配置

**AP 临时实例**（Redis）：
- key：`cosy:capability:ap:{namespace}:{name}:{providerId}`（hash：endpoint/schema/status/lastBeatAt）
- 心跳续约 = 更新 lastBeatAt + 重设 TTL（30s）；过期即消失（Redis TTL 天然摘除）
- 本地缓存 `ConcurrentHashMap<String, List<CapabilityInstance>>` 加速 resolve，心跳/变更时失效重建

**CP 持久实例**（MySQL，可复用 `cosy.agent.task.mysql.*` 连接参数或独立配置）：

```sql
CREATE TABLE IF NOT EXISTS capability_provider (
  provider_id   VARCHAR(64) PRIMARY KEY,
  app_name      VARCHAR(128) NOT NULL,
  base_url      VARCHAR(512) NOT NULL,
  auth_type     VARCHAR(32)  NOT NULL DEFAULT 'shared-secret',
  call_token    VARCHAR(128),
  mode          VARCHAR(8)   NOT NULL,            -- ap | cp
  status        VARCHAR(16)  NOT NULL DEFAULT 'UP',
  last_beat_at  DATETIME(3)  NULL,
  created_at    DATETIME(3)  NOT NULL
);
CREATE TABLE IF NOT EXISTS capability (
  capability_name   VARCHAR(128) NOT NULL,        -- {namespace}_{name}
  provider_id       VARCHAR(64)  NOT NULL,
  description       VARCHAR(1024),
  parameters_schema TEXT,
  endpoint_path     VARCHAR(256) NOT NULL,
  endpoint_method   VARCHAR(8)   NOT NULL,
  retryable         BOOLEAN      NOT NULL DEFAULT FALSE,
  status            VARCHAR(16)  NOT NULL DEFAULT 'UP',
  PRIMARY KEY (capability_name, provider_id)
);
```

**配置段**（application.yml 新增）：

```yaml
cosy:
  agent:
    capability:
      enabled: ${COSY_AGENT_CAPABILITY_ENABLED:false}      # 默认关闭，注册接口与动态注入不生效
      token: ${COSY_AGENT_CAPABILITY_TOKEN:}               # 注册鉴权令牌（空=不校验）
      default-mode: ${COSY_AGENT_CAPABILITY_DEFAULT_MODE:ap}
      heartbeat: { interval: 5s, suspect-after: 15s, expire-after: 30s }
      probe:      { enabled: true, interval: 60s }          # CP 主动健康检查
      store: ${COSY_AGENT_CAPABILITY_STORE:memory}          # memory | redis | mysql（CP 必须 mysql）
      namespace: ${COSY_AGENT_CAPABILITY_NAMESPACE:default}
```

## 10. 降级与运维

| 场景 | 行为 |
| --- | --- |
| 提供者全部 DOWN | 候选链耗尽 → 工具返回可读错误 → 注入 Observation → LLM 自愈/如实回答 |
| 单实例调用超时 | Resilience TOOL 超时 → 标 DOWN → 切下一候选（AP 同时移除心跳续约） |
| 注册中心 Redis 故障 | AP 能力读到本地缓存（最终一致，最多 30s 滞后）；CP 直读 MySQL 不受影响 |
| 能力需要停用 | 管理 API `PUT /api/agent/capabilities/{name}/disable`：从 ToolRegistry 摘除（模型不再看到） |
| 能力升级 | 注册同名前缀新版本（`name@v2` 或覆盖注册），候选链保留旧版过渡 |

## 11. 实施步骤

| 步骤 | 内容 | 验收 |
| --- | --- | --- |
| **A. 模型与注册 API（AP 先行）** | 核心模型 + CapabilityRegistry(内存+Redis) + 注册/心跳/注销 API + 心跳摘除调度 | 注册后目录可见；停心跳 30s 自动摘除 |
| **B. 代理执行器接入 ReAct** | CapabilityProxyTool + resolve 寻址 + 候选链降级 + Resilience TOOL 容错 | Mock/真实 LLM 选中远程能力并成功调用；失败自动切候选 |
| **C. CP 持久化 + 主动探测** | MySQL 表 + CapabilityStore(mysql) + HealthProbe + 强一致注册 | 重启后 CP 能力保留；探测 DOWN 不摘除 |
| **D. 安全与收尾** | 注册令牌 + callToken 调用鉴权 + 命名空间 + 管理 API 开关 + 测试 + 阅读文档更新 | 鉴权开启后未授权注册返回 401；全量测试绿 |

## 12. 边界与后续演进

- **本方案单机先行**：AP 多节点同步（Distro 风格）与 CP 故障转移（Raft/DB 约束）列为二期——与 Nacos 双协议演进的路径一致
- **能力目录订阅推送**：客户端/其他 Agent 可订阅能力变更（SSE 推送 + 轮询兜底），二期
- **注册即用的"能力市场"**：配合 `ModelRoutingAdmin.catalog` 模式，客户端可浏览已注册能力
- 本方案不改动现有本地工具、路由、记忆、RAG 任何行为；`cosy.agent.capability.enabled=false`（默认）时系统与现状完全等价
