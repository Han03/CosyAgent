# CosyAgent 模型管理平台化设计方案

> 目标：把 Agent 的模型配置**统一收敛到客户端设置页**，设置页成为"模型维护 + 能力执行"的平台控制台。
> 定位：CosyAgent 后续是一个**维护模型和执行能力的完整平台**——本方案先完成"模型域"平台化，能力域（注册中心）与任务域（会话/长任务）已就绪，三者最终在设置页合并为统一控制台。

---

## 1. 现状与问题

### 1.1 模型配置目前分散在哪些地方

| 层 | 现状 | 问题 |
|---|---|---|
| 后端 YAML | `application.yml` 的 `cosy.model-routing` 定义默认链（zhipu/glm-4-flash → aliyun/qwen-max → openrouter → volcengine），api-key 在 gitignored 的 `application-local.yml` | 改配置要改文件 + 重启；key 明文落盘 |
| 后端管理 API | 已有模型路由 catalog 查询/热更新（`GET /api/agent/model-routing/catalog` + 管理接口） | 只覆盖目录查询，无平台/模型/规则的完整 CRUD；无连通性测试 |
| 客户端设置页 | 服务地址 / API Key / Mock 开关 / 能力中心 | 模型配置入口缺失（只有目录只读展示雏形） |
| 客户端会话页 | 已有 auto / 指定模型选择器雏形（`X-Cosy-Model` 请求头） | 选择器数据源来自后端目录，目录不完整则选择不可用 |

### 1.2 核心问题

1. **配置入口不统一**：平台/模型/路由散在 YAML + 代码 + 客户端多处，改一处不可见全局。
2. **运维动作缺失**：新增平台、换 key、调整降级顺序、测试连通性——目前都要改文件重启。
3. **平台化目标未闭环**：作为"维护模型和执行能力的完整平台"，需要一套**面向用户的配置域模型 + CRUD API + 设置页 UI**，而不是面向开发者的 YAML。

---

## 2. 目标与设计原则

### 2.1 目标

- 客户端设置页提供**模型管理**完整能力：平台（Provider）增删改、模型（Model）增删改、路由规则（Rule：任务类型 → 有序候选链）编辑、连通性测试。
- 后端仍是**执行权威**：所有配置落库（或内存热更新），请求时按"会话级指定 > 规则链 > 默认链"决策；设置页只是配置 UI，不改变执行模型。
- 变更**即时生效**：保存即热更新，无需重启；运行中会话不受影响（新请求用新配置）。
- **Key 安全**：平台 api-key 写后不回显明文（掩码展示）、支持替换，绝不进日志与目录接口。

### 2.2 设计原则

- **配置域与执行域分离**：配置 CRUD 只管"写什么"，执行器只管"怎么用"；执行器已实现的候选链/降级/超时逻辑不改。
- **向后兼容**：YAML/env 作为种子基线保留；首次写入平台配置后以存储为准（存储 > YAML 基线；env 注入的 key 优先级最高）。
- **一次性到位**：不做"临时配置表 + 后续迁移"，数据模型直接按平台化目标设计。
- **去噪**：字段语义自明的（如 baseUrl）不加冗余说明。

## 3. 配置域数据模型

```
ModelProvider（模型平台）
 ├─ id            platformId（如 zhipu / aliyun / openrouter / volcengine / openai-compatible）
 ├─ name          展示名
 ├─ type          平台类型（枚举：zhipu|aliyun|openrouter|volcengine|openai|ollama|自定义）
 ├─ baseUrl       兼容 OpenAI 的请求根地址
 ├─ completionsPath 补全路径（默认 /chat/completions）
 ├─ apiKey        密文存储，接口只回显掩码
 ├─ enabled       启用开关
 ├─ timeoutMs     单请求超时
 └─ props         平台扩展属性（如 zhipu 的 extra 字段映射）

ModelSpec（平台下模型）
 ├─ id            modelId（如 glm-4-flash / qwen-max / gpt-4o）
 ├─ providerId    归属平台
 ├─ displayName   展示名（可选，缺省用 modelId）
 ├─ contextWindow 上下文长度（用于 Agent 决策截断/提示）
 └─ capabilities  能力标签（chat | tool-call | vision | long-context）

RouteRule（路由规则：任务类型 → 有序候选链）
 ├─ taskType      任务类型（default | agent | chat | tool | 扩展名）
 ├─ candidates    [ {providerId, modelId}, ... ] 按顺序降级
 └─ lockMode      是否锁定（锁定时不跨模型降级，用于会话级指定模型）

RuntimeSelection（会话级覆盖，已有雏形）
 ├─ sessionId / 请求级 X-Cosy-Model 头
 └─ selection     auto | providerId/modelId
```

关系：`Provider 1—N Model`；`Rule 1—N Candidate`（有序）；会话级 Selection 覆盖 Rule。

## 4. 后端设计

### 4.1 存储与加载优先级（一次到位）

```
请求决策：会话级 X-Cosy-Model > 该任务类型 RouteRule > default 规则 > YAML 种子基线
Key 注入：env（COSY_AGENT_MODEL_*）> 库中平台 apiKey > YAML 基线
```

- 新增配置存储：复用现有 MySQL（业务数据已支持），建表 `model_provider`、`model_rule`；`store=memory` 时退化为运行时配置（不重启丢）。
- 启动：若库中无数据 → 用 YAML 基线构建默认 provider/rule 写入；有数据 → 以库为准（env 注入的 key 覆盖）。
- 热更新：PUT 任一配置后刷新执行器内部的路由表（现有 catalog/决策逻辑不变，只换数据源）。

### 4.2 管理 API（设置页后端）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/agent/model-routing/providers` | 平台列表（apiKey 仅返回掩码 `zhipu****abc`） |
| POST | `/api/agent/model-routing/providers` | 新增平台（apiKey 必填一次，落库加密） |
| PUT | `/api/agent/model-routing/providers/{id}` | 更新平台（apiKey 可空=保持不变；非空=替换） |
| DELETE | `/api/agent/model-routing/providers/{id}` | 删除平台（级联删除其模型；有规则引用则拒绝） |
| POST | `/api/agent/model-routing/providers/{id}/models` | 平台下新增模型 |
| PUT/DELETE | `/api/agent/model-routing/providers/{id}/models/{modelId}` | 改/删模型 |
| GET/PUT | `/api/agent/model-routing/rules` | 路由规则整体读写（有序候选链） |
| POST | `/api/agent/model-routing/test` | 连通性测试：body {providerId, modelId, prompt?} → 真实最小请求，返回耗时/结果或错误 |
| GET | `/api/agent/model-routing/catalog` | 目录（脱敏，供会话页选择器）——现有接口保留 |

鉴权：全部走现有 `X-API-Key` 体系；apiKey 字段在任何响应/日志/目录接口中**不得出现明文**。

### 4.3 执行器适配

- 现有 `ModelRouter`（catalog 决策、候选链、降级）**不改核心逻辑**，只把配置来源从 YAML 常量改为上面存储的 provider/rule。
- 连通测试复用现有调用栈（走 Resilience4j TOOL 容错），超时统一 `timeoutMs`。
- 会话级锁定语义保留：`X-Cosy-Model: provider/model` 时单候选执行、不跨模型降级。

## 5. 客户端设置页设计（平台控制台）

### 5.1 设置页 Tab 化

```
设置
 ├─ 连接     服务地址 / API Key / Mock 开关 / 测试连接（现状保留）
 ├─ 模型管理  ← 本次新增（统一入口）
 ├─ 能力中心 已有（能力注册中心目录）
 └─ 日志     已有日志查看（后续可并入）
```

### 5.2 模型管理页交互

**一级：平台列表**
- 卡片式列表：平台名 + 类型 + 状态（启用/停用 + 连通性圆点）+ 模型数 + key 掩码。
- 操作：新增平台（表单：id/name/type/baseUrl/completionsPath/timeout/apiKey）、编辑、启用停用、删除、**测试连通**。
- 新增平台表单的 apiKey 必填一次；编辑时掩码展示、留空=保持不变。

**二级：平台详情 → 模型列表**
- 该平台下模型：modelId、displayName、contextWindow、capabilities 标签。
- 操作：新增模型、编辑、删除。

**三级：路由规则**
- 任务类型列表（default/agent/chat/tool…）：每条规则 = 有序候选链。
- 编辑：从平台×模型中逐项选择（最多 N 个），上移/下移调整**降级顺序**；可锁定。
- 展示"auto（默认链）"与"指定模型"两种效果说明。

**会话页联动**：会话顶栏模型选择器（auto | 具体模型）数据源 = catalog；选择"具体模型"时请求带 `X-Cosy-Model`，锁定不降级——与市场 agent 工具一致。

### 5.3 关键 UX 规则

- 所有变更**保存即热更新**，页面给"已生效"反馈；不提示重启。
- 删除平台有二次确认 + 引用提示（被规则引用不可删）。
- 连通性测试失败给出可读原因（超时/鉴权/网络），不暴露 key。
- 手机端窄屏：平台列表/详情/规则三页均可滚动，操作按钮不溢出。

## 6. 安全设计

- **apiKey 存储**：后端 AES 加密落库（密钥 env 注入）；接口只回显掩码；日志过滤 `apiKey`/`Authorization` 字段。
- **传输**：管理 API 全走 HTTPS（部署时），本地走现有 X-API-Key 鉴权。
- **测试连通**：用存储的 key 发起最小请求，绝不把 key 回传给前端做直连测试（避免 key 出库）。
- **审计**：平台/规则变更记录到现有日志模块（谁改了什么、何时改）。

## 7. 实施分期与验收

### Step 1：后端配置域（1 次到位）
- 建表/存储适配（memory|mysql）、YAML 种子基线迁移、Provider/Model/Rule CRUD API、key 加密与掩码、连通性测试 API、执行器数据源切换。
- 验收：`mvn test` 全绿（新增配置域单测：CRUD/掩码/级联删除/优先级）；curl 全链路（增平台→加模型→配规则→test→catalog）。

### Step 2：客户端模型管理 UI
- 设置页 Tab 化 + 平台列表/新增/编辑/删除/测试连通 + 模型管理 + 路由规则编辑（候选链排序）+ 会话选择器接 catalog。
- 验收：`flutter analyze` 0 issues；桌面端/手机端手测全流程；**不截图**（启动不报错 + 关键交互日志）。

### Step 3：平台控制台合并
- 设置页统一为"连接 / 模型 / 能力 / 日志"控制台；会话页展示当前生效链路（会话 → 任务类型 → 候选链 → 实际模型）以便排查。
- 验收：端到端：设置页配新平台新模型 → 会话 auto 走新链 → 真实对话成功；指定模型 → 锁定该模型。

### 里程碑检查
- [ ] 配置域：平台/模型/规则全部可在设置页维护，后端即时生效，无需重启
- [ ] Key 安全：明文只出现在首次录入，任何查询/日志/目录均掩码
- [ ] 连通性：每个平台可一键测试，失败原因可读
- [ ] 兼容：现有 YAML 配置无需迁移即可启动；env key 注入优先级最高
- [ ] 平台化：能力中心 + 模型管理 + 会话/任务在设置页合并为统一控制台

## 8. 边界与后续

- **不改变执行模型**：候选链/降级/超时/会话锁定的运行时语义与现状一致，只是配置来源统一。
- **多实例一致性**：MySQL store 下多实例共享配置；memory store 仅单实例演示（文档注明）。
- **后续可扩展**：模型评测（同一任务多模型对比）、成本统计（按 provider 计费）、规则按会话模板复用——数据模型已为这些预留（capabilities/contextWindow/props）。
