# 第三方能力接入设计方案

> 目标：让 CosyAgent 能力中心可以直接注册**第三方 HTTP API**（如免费天气服务），
> 并且**在前端（客户端设置页能力中心）可视化配置**，无需手工 curl。
> 核心扩展：注册协议增加**认证模型**（API Key / Token），提供者信息可管理、可脱敏回显。

---

## 1. 背景与目标

### 1.1 现状

能力注册中心（CapabilityRegistry，参考 Nacos AP/CP 设计）已支持：

- 外部项目注册能力：`POST /api/capabilities/register`（appName + baseUrl + capabilities[]）
- 能力目录：`GET /api/agent/capabilities`（脱敏）
- 调用语义：`sync`（直连）/ `submit-poll`（提交→轮询→取结果）；GET 参数走 query、POST 走 body、`{arg}` 走路径模板
- Agent 侧：`dynamicTools()` 每轮实时将注册表生成为工具定义，**注册即可用**

### 1.2 差距（本方案解决的问题）

| # | 差距 | 影响 |
|---|---|---|
| 1 | 注册协议**没有认证字段**（API Key / Token） | 需 key 的第三方 API（和风、OpenWeatherMap 等）无法直接注册，只能靠无 key 服务或自建薄代理 |
| 2 | 注册只能通过 **HTTP API 手工调用**（curl/脚本） | 前端无法可视化配置，非工程用户不可用 |
| 3 | 已注册提供者**无法管理**（查看/编辑/删除入口缺失，deregister 需知道 providerId） | 配置不可维护、不可审计 |

### 1.3 目标

1. 注册协议支持**认证模型**：无 / Bearer Token / 自定义请求头 / URL 查询参数，四种模式覆盖主流第三方 API
2. 认证密钥**加密落库、目录脱敏、日志过滤**（复用模型管理平台的 ApiKeyCipher 机制）
3. 客户端**能力中心 Tab** 支持可视化：添加第三方能力（提供者 + 能力列表）、编辑、删除、连通性展示
4. 与既有"外部项目注册"完全兼容：同一注册逻辑、同一目录、来源可区分

## 2. 总体设计

### 2.1 认证模型（提供者级）

注册协议在**提供者（provider）维度**增加认证配置，四种模式：

| authType | 含义 | 请求携带方式 | 适用场景 |
|---|---|---|---|
| `none` | 无认证（默认，兼容现状） | — | Open-Meteo、wttr.in 等免费无 key API |
| `bearer` | Bearer Token | `Authorization: Bearer {authValue}` | 多数商业 API 的 Token 鉴权 |
| `header` | 自定义请求头 | `{authHeaderName}: {authValue}` | 如 `X-API-Key: xxx`、`apikey: xxx` |
| `query` | URL 查询参数 | `{baseUrl}{path}?{authParamName}={authValue}` | 如 OpenWeatherMap `appid=xxx`、和风 `key=xxx` |

字段：

```json
{
  "appName": "open-meteo",
  "baseUrl": "https://api.open-meteo.com",
  "mode": "cp",
  "namespace": "weather",
  "authType": "none",              // none | bearer | header | query
  "authHeaderName": null,          // authType=header 时必填，如 "X-API-Key"
  "authParamName": null,           // authType=query 时必填，如 "appid"
  "authValue": "sk-xxx",           // 敏感：仅写入时传入，加密落库，永不回显
  "capabilities": [ ... ]
}
```

约束：

- `authType=header` 时 `authHeaderName` 必填；`authType=query` 时 `authParamName` 必填；`authType=bearer/none` 时两者忽略
- `authValue` 为空且提供者已存在（编辑场景）→ 保持原值不回写（与模型管理 updateProvider 的 api-key 语义一致）
- `query` 模式密钥会出现在 URL 中（第三方限制所致），设计上保留但 UI 标注风险提示

### 2.2 数据结构与存储（MySQL）

`capability_provider` 表扩展列（`ALTER TABLE ADD COLUMN IF NOT EXISTS`，兼容旧库）：

| 新列 | 类型 | 说明 |
|---|---|---|
| `auth_type` | VARCHAR(16) | 默认 `none` |
| `auth_header_name` | VARCHAR(64) | header 模式头名，默认 NULL |
| `auth_param_name` | VARCHAR(64) | query 模式参数名，默认 NULL |
| `auth_value_encrypted` | VARCHAR(512) | **AES/CBC 加密**（复用 ApiKeyCipher，env `COSY_AGENT_MODEL_KEY_SECRET`），默认 NULL |

- `CapabilityProvider` record 增加对应字段；`MysqlCapabilityStore.save/loadProviders` 加密写、解密读（解密失败原样返回兼容旧数据）
- Memory store：仅内存镜像，认证值同样以密文形态持有（AP 场景由 Registry 权威管理）

### 2.3 调用链路（认证注入）

`CapabilityRegistry.invoke`（sync）与 `invokeSubmitPoll`（提交/轮询/结果三步）统一在构造请求时注入认证：

```
sync:     GET/POST {baseUrl}{path}?params      → 按 authType 注入
submit:   POST {baseUrl}{path}                 → 按 authType 注入
poll:     GET  {statusPath/resultPath}         → 按 authType 注入
```

注入逻辑（单一 `applyAuth(headers, uri, provider)`）：

- `none`：不注入
- `bearer`：`header("Authorization", "Bearer " + authValue)`
- `header`：`header(authHeaderName, authValue)`
- `query`：URI 追加 `authParamName=authValue`（用 UriBuilder 正确编码）

始终保留既有 `X-Capability-Call-Token` 头（CosyAgent → 提供者自家令牌，与第三方认证并存，互不冲突）。

### 2.4 API 设计（管理端点）

在 `CapabilityController` 增加提供者管理端点（前缀 `/api/agent/capabilities`，与目录同域）：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/agent/capabilities/providers` | 提供者列表：providerId / appName / baseUrl / authType / **authValue 掩码**（`sk-****`）/ mode / 状态 / 能力数 / 创建时间 |
| GET | `/api/agent/capabilities/providers/{providerId}` | 提供者详情：含能力完整列表（参数/端点/模式），供编辑回显 |
| POST | `/api/agent/capabilities/providers` | 创建第三方能力提供者（body 同 RegisterRequest + 认证字段）→ 复用 `registry.register`，返回 providerId/callToken |
| PUT | `/api/agent/capabilities/providers/{providerId}` | 更新：appName/baseUrl/认证/能力全量覆盖；`authValue` 空保持原值 |
| DELETE | `/api/agent/capabilities/providers/{providerId}` | 删除（= deregister，级联删能力） |

复用关系：

- **POST providers = 外部 register 的管理端等价入口**（同一 `registry.register`，来源一致；外部项目注册与前端配置最终落在同一目录，新增 `source` 标记：`external`（带 X-Capability-Token 调用）/ `console`）
- 心跳/探活/目录逻辑全部不变

### 2.5 客户端配置 UI（能力中心 Tab）

能力中心 Tab 由"只读目录"升级为"目录 + 提供者管理"：

```
能力中心（Tab）
├── 能力目录（只读，来源徽标：外部注册 / 控制台）
│    每项：能力名 · 描述 · 提供者（baseUrl + 状态点 UP/DOWN）· 端点/模式
└── 「添加第三方能力」按钮 → 提供者表单页
      ├── 基本信息：名称(appName) · baseUrl · 模式(AP/CP) · 命名空间
      ├── 认证：类型下拉(无/Bearer/自定义头/URL参数) + 对应字段（密钥为密码输入框）
      ├── 能力列表编辑器（动态增删行）：
      │    名称 · 描述 · 参数JSON · 端点路径 · 方法(GET/POST) · 模式(sync/submit-poll)
      │    （submit-poll 时展开 状态路径/结果路径/轮询间隔/超时）
      └── 保存 → POST providers → 目录刷新
现有提供者：每项「编辑」（回显掩码密钥）/「删除」（确认后 DELETE）
```

交互细节：

- 密钥输入：`obscureText: true`；编辑回显仅显示掩码 + "留空保持不变"
- 参数 JSON 输入：带语法校验（非法 JSON 保存前提示）
- 能力中心与目录同数据源：保存/删除后 `_reload()`
- 客户端 API：`api_client` + `system_repository` 新增 4 个接口（providers 列表/详情/创建/更新/删除）

### 2.6 安全设计

| 项 | 方案 |
|---|---|
| 密钥存储 | AES/CBC 加密落库（复用 ApiKeyCipher，密钥 env `COSY_AGENT_MODEL_KEY_SECRET`，缺省 DEV_KEY + 启动告警） |
| 目录/列表 | `authValue` 一律掩码（`****`），列表与详情均不回显明文 |
| 日志 | 认证值不进入日志：调用日志仅记 authType 与 providerId |
| 请求 | 仅存内存态解密后注入请求头，不落日志、不返回响应 |

## 3. 测试与验收

### 3.1 单元/集成测试

| 用例 | 断言 |
|---|---|
| `applyAuth` 四种模式 | bearer/header/query/none 分别产生正确请求头/URI（含 URL 编码） |
| provider 管理 CRUD | 创建（认证加密落库）→ 列表掩码 → 更新（authValue 空保持）→ 删除 |
| query 模式 URI 拼接 | 已有 query 参数时 `&` 连接正确 |
| 兼容 | 旧 provider（无认证列）load 正常、调用不带认证头 |

### 3.2 端到端冒烟（验收路径）

1. 前端添加"Open-Meteo 天气"提供者（authType=none）：
   - appName=`open-meteo`，baseUrl=`https://api.open-meteo.com`
   - 能力 `forecast`：GET `/v1/forecast`，参数 `latitude/longitude/current_weather`
2. 目录出现 `weather_forecast`，状态 UP
3. Agent 提问"查询上海当前天气" → 工具调用返回真实天气数据（跨公网链路验证）
4. 需 key 场景（可选）：本地起薄代理或注册支持 header 的 mock 服务，验证 bearer/header 注入
5. `flutter analyze` 0 issues + 后端全量测试全绿 + 重启后提供者持久化恢复

## 5. 兼容性与回退

- 旧注册请求（无认证字段）→ 默认 `authType=none`，行为与现状完全一致
- 旧库表无新列 → 启动 `ALTER TABLE ADD COLUMN IF NOT EXISTS` 自动补齐
- 目录 API 结构向后兼容（新增字段不破坏既有客户端）
- 认证值解密失败（密钥变更）→ 原样返回密文并告警，不阻断服务
