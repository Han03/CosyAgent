# 大模型调用记录设计方案

> 目标：为 CosyAgent 建立 **LLM 调用全链路可追溯、可审计、可分析** 的调用记录体系。
> 覆盖：路由决策（候选链/降级）、每次候选尝试的耗时与失败原因、Token 用量、
> 与会话/任务/ReAct 轮次的关联，以及按时间/模型/路由类型的统计报表。
> 原则：**记录不阻断业务、内容明文可排查、埋点不侵入模型调用**。

---

## 1. 背景与目标

### 1.1 现状

`ModelRouter.call(prompt, modelChoice, routeType)` 是全部 LLM 调用的统一入口：
候选链循环 → 每候选套 Resilience4j 容错 → 可降级异常切换下一候选。
`RouteResult` 已携带 `attempts`（实际尝试序列）与 `reasons`（降级原因），但**调用结束后即丢失**。

### 1.2 动机（调用记录解决什么）

| 场景 | 现状痛点 |
|---|---|
| 成本核算 | 无法统计各平台/模型的实际 Token 消耗与费用 |
| 稳定性监控 | 无法量化失败率、降级率、P95 延迟 |
| 路由效果分析 | 无法证明"default/reasoning 链 + 降级"是否真在按预期工作 |
| 故障排查 | 会话报错时无法回溯"当时调了哪个模型、为什么降级" |
| 审计合规 | 企业环境需要留痕（谁/何时/哪个模型/什么任务） |

### 1.3 设计原则

1. **埋点统一**：只在 `ModelRouter` 层采集（代理/模板方法），不侵入 ChatModel 实现
2. **异步不阻塞**：记录走内存队列 + 批量落库；队列满丢弃并告警，绝不影响主请求
3. **内容明文（开发阶段）**：开发/排查阶段完整记录 Prompt/Response 明文，便于定位 prompt 构造、工具调用输入输出、模型回答异常等问题；预留内容策略开关（明文/截断/关闭），上线前切换
4. **上下文贯通**：通过 `LLMCallContext`（ThreadLocal）把 sessionId/taskId/iteration/toolName 传入记录
5. **可分析**：聚合统计 API 支持按时间/模型/路由类型/状态分组

## 2. 总体架构

```
Agent 调用链                          LLM 调用记录链
─────────────────                    ───────────────────────────────
DefaultReActAgent (每轮)              ┌─ LLMCallContext(ThreadLocal)
   │ 设置 sessionId/taskId/iter        │   sessionId / taskId / iteration / toolName
   ▼                                  ▼
ModelRouter.call(...) ──────────► CallRecorder.beginCall(...)
   │  路由决策(候选链/routeType)        │   生成 traceId、记请求内容/时间
   ▼                                  ▼
for candidate in chain                CallRecorder.beginAttempt(candidate)
   │  callCandidate(...) ──────────►    │   记平台/模型/开始时间
   │  resilience.execute(LLM)          │
   │  ChatResponse(含 usage)           │   callCandidate 返回后记 usage/耗时/成功
   │  异常 → classify() ──────────►    │   记失败原因（熔断/超时/连接/HTTP）
   ▼                                  ▼
RouteResult(attempts/reasons)        CallRecorder.endCall(...) —— 记最终命中/总耗时
                                     └─► 异步队列 → @Scheduled 批量落库 MySQL
                                                    │
                                                    ▼
                              llm_call_log 表 ← 查询/统计 API ← 客户端"调用记录"Tab
```

**埋点位置说明**：

- `call()` 入口/出口：一次调用（含全部候选尝试）的整体记录
- `callCandidate()` 每次候选：attempt 级明细（含 Resilience4j 重试在内部，record 一次最终结果）
- 上游 `DefaultReActAgent`/`AgentOrchestrator` 在调用前设置 `LLMCallContext`（每轮迭代、工具调用分别标记），调用后清理

## 3. 数据模型（MySQL）

`CREATE TABLE llm_call_log`（复用 cosy 库，`cosy.agent.llmlog` 开关控制装配，默认启用）：

```sql
CREATE TABLE IF NOT EXISTS llm_call_log (
  id                BIGINT AUTO_INCREMENT PRIMARY KEY,
  trace_id          VARCHAR(64)  NOT NULL,          -- 一次模型调用链路 id（含候选降级）
  session_id        VARCHAR(64)  NULL,              -- 关联会话
  task_id           VARCHAR(64)  NULL,              -- 关联 agent 任务
  iteration         INT          NOT NULL DEFAULT 0,-- ReAct 轮次
  tool_name         VARCHAR(64)  NULL,              -- 工具调用上下文（工具名）
  route_type        VARCHAR(32)  NOT NULL DEFAULT 'default', -- default | reasoning | auto
  model_choice      VARCHAR(128) NOT NULL,          -- 调用方选择（auto 或 平台/模型）
  candidate_chain   VARCHAR(512),                   -- 候选链（逗号分隔，决策快照）
  attempts          VARCHAR(512),                   -- 实际尝试序列
  reasons           TEXT         NULL,              -- 降级原因列表（JSON 数组）
  chosen_model      VARCHAR(128) NULL,              -- 最终命中（平台/模型）
  status            VARCHAR(16)  NOT NULL,          -- SUCCESS | FAILED
  error_msg         VARCHAR(512) NULL,              -- 全部失败时的聚合错误
  prompt_content     MEDIUMTEXT   NULL,              -- 输入明文（开发阶段；上线可切换截断/关闭）
  response_content   MEDIUMTEXT   NULL,              -- 输出明文
  prompt_tokens     INT          NULL,              -- SpringAI usage.promptTokens
  completion_tokens INT          NULL,              -- usage.completionTokens
  total_tokens      INT          NULL,              -- usage.totalTokens
  latency_ms        INT          NOT NULL DEFAULT 0,-- 总耗时（含降级链）
  started_at        DATETIME(3)  NOT NULL,
  finished_at       DATETIME(3)  NOT NULL,
  KEY idx_session   (session_id, started_at),
  KEY idx_model     (chosen_model, started_at),
  KEY idx_status    (status, started_at),
  KEY idx_trace     (trace_id)
) DEFAULT CHARSET=utf8mb4
```

**字段口径**：

- `status=FAILED`：全部候选失败（路由抛聚合异常）；单候选失败属降级，`status=SUCCESS` 但 `reasons` 非空
- `prompt_content/response_content`：开发阶段写入完整明文（MEDIUMTEXT，单条上限 16MB，实际对话远小于此）；内容策略开关 `cosy.agent.llmlog.content-mode=plain|truncated|none`（默认 plain），上线切 truncated（截断 N 字符）或 none（仅留字符数与 token）
- Token：读 `ChatResponse.getMetadata().getUsage()`（PromptUsage）；不可得（mock/自定义模型）留 NULL
- `iteration`：ReAct 每轮自增；工具调用场景 `tool_name` 记录触发工具

**存储选型**：MySQL 主存储（与任务/会话同库，事务一致）；不做 Redis/PG 分流——调用量级（个人/内部 Agent）单表足够，索引覆盖查询与统计。量大时后续可加分区（按月）。

## 4. 采集实现

### 4.1 LLMCallContext（上下文贯通）

```java
/** 当前模型调用的业务上下文（每轮 ReAct/工具调用设置，调用后清理）。 */
public final class LLMCallContext {
    private static final ThreadLocal<Context> CTX = new ThreadLocal<>();

    public record Context(String sessionId, String taskId, int iteration, String toolName) {}

    public static void set(Context ctx) { CTX.set(ctx); }
    public static Context get() { return CTX.get(); }
    public static void clear() { CTX.remove(); }
}
```

- `DefaultReActAgent.run()` 每轮迭代前 `LLMCallContext.set(...)`，迭代结束清理
- `CapabilityProxyTool`/本地工具执行回调模型（工具结果总结）时带 `toolName`

### 4.2 CallRecorder（记录器 + 异步落库）

```java
@Component
@ConditionalOnProperty(prefix = "cosy.agent.llmlog", name = "enabled", havingValue = "true", matchIfMissing = true)
public class CallRecorder {
    private final LinkedBlockingQueue<LlmCallLog> queue = new LinkedBlockingQueue<>(10_000);
    // beginCall → 构造记录（traceId/上下文/请求内容/startedAt）
    // beginAttempt(candidate) → 记录候选尝试（attempts 追加 + 失败原因）
    // endCall(response | failure) → usage/耗时/状态 → 入队
    // @Scheduled(fixedDelay=5s) flush() → 批量 INSERT（JDBC batch），失败记录到日志并丢弃（不阻断业务）
    // 队列满：丢弃 + log.warn（保护内存）
}
```

- **写入路径**：`JdbcLlmCallLogStore`（原生 JDBC，仿 `MysqlCapabilityStore` 同款：自建表、batch insert、`cosy.agent.llmlog` 配置段）
- **失败策略**：落库失败仅告警，调用链不受影响（记录是旁路）

### 4.3 ModelRouter 埋点

`ModelRouter` 注入 `CallRecorder`（可空：未装配则跳过，保持路由兼容），改造点最小化：

```
call() 入口    → recorder.beginCall(...)（候选链/routeType/请求内容快照）
候选循环       → recorder.beginAttempt(candidate) / 失败时 recorder.attemptFailed(candidate, reason)
                成功时 recorder.attemptSucceeded(...)（usage/耗时）
call() 出口    → recorder.endCall(chosenModel | failure, latencyMs)
```

- 路由关闭回退分支、空候选回退分支同样记录（chosenModel="default"）
- 记录不改变任何现有返回值与异常语义

### 4.4 内容记录策略（开发阶段明文，预留上线脱敏）

- 开发阶段：`content-mode=plain`，`prompt_content/response_content` 写入完整明文，用于问题排查（定位 prompt 构造错误、工具调用输入输出、模型回答异常）
- 预留切换（上线前改配置即可，代码同一路径）：
  - `truncated`：写开头 N 字符（`content-chars=2000`），省略号结尾
  - `none`：一律 NULL，仅留字符数与 token
- 配置项：
  - `cosy.agent.llmlog.content-mode=plain|truncated|none`（默认 plain）
  - `cosy.agent.llmlog.content-chars=2000`（truncated 模式截断长度）
- 明文内容仅在数据库/管理 API 内可见，不写入应用日志

## 5. API 设计

`LlmCallLogController`（前缀 `/api/agent/llm-logs`，走既有管理鉴权）：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/agent/llm-logs` | 分页列表：`page/size/sessionId/model/routeType/status/start/end`，返回记录行（traceId/模型/状态/耗时/token/明文内容） |
| GET | `/api/agent/llm-logs/{id}` | 单条详情（含 reasons/attempts 全量） |
| GET | `/api/agent/llm-logs/stats` | 聚合统计：`start/end/groupBy=day\|model\|routeType\|status`，返回每组：调用次数、成功率、平均/最大耗时、**P95 耗时**、总 token（in/out/total）、降级次数 |

**统计 SQL 口径**（原生 JDBC 聚合）：

- 按天/模型/路由类型分组计数
- 成功率 = `SUCCESS 数 / 总数`（含降级成功）
- 降级次数 = `reasons 非空 且 SUCCESS`
- P95 耗时：`ORDER BY latency_ms LIMIT offset,1`（或 PERCENTILE 近似：按组取出 latency 数组客户端算——记录量小，取明细数组更简单可靠）

## 7. 兼容性与回退

- 开关关闭（`cosy.agent.llmlog.enabled=false`）：CallRecorder 不装配，ModelRouter 无感，行为与现状一致
- 旧库：`CREATE TABLE IF NOT EXISTS` 自建
- 记录失败（队列满/落库异常）：业务调用零影响，仅日志告警
- 统计接口在无数据时返回空分组，不报错
