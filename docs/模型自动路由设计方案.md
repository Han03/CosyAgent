# 模型自动路由设计方案（Auto 决策层）

> 版本：v2.1（在 v2.0 候选链 + 降级基础上补"选链决策层"）
> 关联：`模型路由设计方案.md`（v2.0）、`大模型调用记录设计方案.md`（决策数据源）
> 目标：auto 模式不再固定走 default 链，而是**按任务特征动态决策**（选链 + 排序候选），
> 对齐主流 Agent 工具的"Auto 自动选模型"；手动指定模型保留为高级选项。

---

## 1. 背景与目标

### 1.1 现状（v2.0）

- `auto` → `RouteConfig.resolveCandidates()` 按 routeType 取**静态链**（缺省 default），链序写死
- 路由类型只有 default / reasoning 两条，与任务内容无关
- 降级按声明顺序尝试，不能按任务动态排序
- 手动指定 = 逃生通道（用户知道用哪个模型更好，但路由层不会自己判断）

### 1.2 目标

1. **auto = 动态决策**：路由引擎按任务特征（问题内容 / 工具需求 / 上下文长度 / 历史表现）选择链并排序候选
2. **零成本起步**：L1 规则化（任务标签 → 链）不引入额外模型调用；L2 画像打分排序；L3（远期）LLM Router
3. **手动指定保留**：客户端 Auto 默认 + 指定模型高级选项（与豆包/主流 Agent 一致）
4. **决策可解释**：每次决策输出"原因"（命中哪些特征、分数排序），随调用记录落库，可审计可调优
5. **闭环进化**：调用记录（成功率/延迟/降级率）回流为决策打分输入，数据越用越准

### 1.3 设计原则

- **决策层可插拔**：`RouteDecisionProvider` 接口 + 多实现，默认实现 = 现状（静态链），行为零变化
- **不新增调用链开销**：L1/L2 决策在本进程内完成，不调模型（L3 才引入一次小模型调用）
- **决策失败降级**：决策器异常/无数据 → 回退静态链，绝不影响主请求
- **与 v2.0 兼容**：请求协议（`X-Cosy-Model` / `X-Cosy-Route-Type`）、降级语义、客户端交互全部不变

## 2. 决策模型

### 2.1 三层演进（可独立落地）

| 层级 | 名称 | 决策依据 | 开销 | 阶段 |
|---|---|---|---|---|
| L0 | 静态链（现状） | routeType → 固定链 | 0 | 已实现 |
| **L1** | 任务标签路由 | 输入特征命中标签 → 选链 | 0（纯规则） | **本期** |
| **L2** | 画像打分排序 | 任务需求 × 模型画像评分 → 动态排序候选 | 0（进程内计算） | **本期** |
| L3 | LLM Router（预留） | 小模型/分类器决策选模型 | 1 次小模型调用 | 远期 |

### 2.2 调用链（auto 模式下）

```
请求(auto) ──► RouteDecisionProvider.decide(RouteContext)
                    │
                    ├─ L1: 特征提取 → 任务标签 → 选链（如 tool-heavy 链）
                    ├─ L2: 画像打分 → 候选按分数排序（高→低）
                    └─ 无命中/失败 → 回退 L0 静态链（现状行为）
                    │
                    ▼
              有序候选链 ──► 现有降级执行（ModelRouter 不变）
```

### 2.3 RouteContext（决策输入）

```java
public record RouteContext(
        String modelChoice,          // auto | 指定模型（指定则绕过决策器）
        String routeType,            // 显式路由类型（有则优先，决策器不覆盖）
        List<Message> messages,      // 本次完整消息序列（含历史）
        List<FunctionTool> tools,    // 动态工具定义（工具数量/复杂度）
        int iteration,               // ReAct 轮次
        SessionProfile session       // 会话画像：历史长度/模型偏好/调用记录统计
) {}
```

**特征提取（从 RouteContext 计算，进程内）**：

| 特征 | 计算方式 | 用途 |
|---|---|---|
| 问题复杂度 | 首条用户消息长度/问句/代码块/列表等启发式 | 简单→轻量链；复杂→强推理链 |
| 工具需求 | `tools` 数量与工具名（是否触发能力/搜索类） | 工具多→tool-heavy 链 |
| 上下文规模 | 消息序列估算 token（字符/4 近似） | 超窗口→长上下文链 |
| 任务类型标签 | 关键词/意图启发式（写作/代码/推理/查询…） | 标签 → 链映射 |
| 历史表现 | `llm_call_log` 统计（按模型：成功率/P95/降级率，近 7d） | L2 打分输入 |
| 会话阶段 | `iteration`（首轮 vs 多轮工具迭代） | 多轮后偏向稳定性链 |

### 2.4 决策输出

```java
public record RouteDecision(
        String rationale,            // 决策原因（可读文本，落库/日志）
        List<String> candidates,     // 有序候选链（最终交给 ModelRouter）
        RouteDecisionMode mode       // STATIC | TASK_TAG | SCORED
) {}
```

## 3. L1 任务标签路由（规则化）

### 3.1 路由类型扩展（配置层）

v2.0 的 `routes` 从两条扩展为多标签链（默认仍提供）：

```yaml
routes:
  default:        [openai/gpt-4o-mini, deepseek/deepseek-chat]   # 通用轻量（L0 兼容）
  reasoning:      [openai/gpt-4o, deepseek/deepseek-reasoner]    # 强推理
  tool-heavy:     [openai/gpt-4o, openai/gpt-4o-mini]            # 工具调用密集
  long-context:   [openai/gpt-4o, qwen/qwen-long]                # 超长上下文
  creative:       [deepseek/deepseek-chat, openai/gpt-4o-mini]   # 创作/发散
```

- 链缺失回退 `default`（现有 `resolveCandidates` 逻辑不变）
- 管理 API 直接可配（v2.0 已有 PUT 全量更新，无需新端点）

### 3.2 特征 → 标签映射（启发式规则表）

| 触发条件 | 标签 | 说明 |
|---|---|---|
| 工具数量 ≥ 3 或含能力类工具 | `tool-heavy` | 工具调用密集，选工具支持强的模型 |
| 消息序列估算 > 模型窗口 60% | `long-context` | 防截断 |
| 命中推理特征（"为什么/推导/证明/分析"/代码片段/数学） | `reasoning` | 强推理 |
| 命中创作特征（"写/创作/故事/文案/润色"） | `creative` | 发散生成 |
| 均未命中 | `default` | 兜底 |

- 规则表在配置段维护（`cosy.agent.model-routing.auto-rules`），可热更新，**不写死在代码**
- 优先级：long-context > tool-heavy > reasoning/creative > default（长上下文与工具优先保可用性）

## 4. L2 画像打分排序（模型匹配）

### 4.1 ModelSpec 画像增强

```yaml
platforms:
  openai:
    models:
      - model-id: gpt-4o-mini
        context-window: 128000
        capabilities: [chat, tool, fast, cheap]      # 已有
        speed: 5            # 响应速度档位 1-5（5=最快）
        reasoning: 2        # 推理强度 1-5
        tool-support: 5     # 工具调用稳定度 1-5
        price-tier: 1       # 成本档位 1-5（5=最贵）
      - model-id: gpt-4o
        context-window: 128000
        capabilities: [chat, tool, reasoning]
        speed: 3
        reasoning: 5
        tool-support: 5
        price-tier: 4
```

- 画像字段：`speed / reasoning / tool-support / price-tier / contextWindow(已有)`
- 均为管理 API 可编辑的元数据（模型管理平台化已有三层 CRUD，扩展字段即可）

### 4.2 打分公式

对候选链中每个候选 `c`（默认对整链打分排序，链外模型不引入——保持 catalog 口径）：

```
score(c) = w1·taskReasoning(c) + w2·taskTools(c) + w3·fitContext(c)
         + w4·reliability(c)   + w5·speed(c) - w6·price(c)

taskReasoning(c) = min(需求推理强度, c.reasoning) 归一化   # 需求≥2 才计入
taskTools(c)     = min(需求工具强度, c.tool-support) 归一化
fitContext(c)    = contextWindow 足够覆盖估算 token ? 1 : 0.3
reliability(c)   = 近7d 成功率×权重 + (1 - 降级率)           # 来自调用记录；无数据=0.5
speed(c)         = c.speed / 5
price(c)         = (c.price-tier - 1) / 4
```

- 权重 `w1..w6` 走配置（默认：推理 0.3 / 工具 0.2 / 上下文 0.2 / 可靠性 0.15 / 速度 0.1 / 价格 -0.05）
- 输出：候选按 score 降序；分数相同保持声明顺序（稳定排序）
- **可靠性数据缺失**（无调用记录/新模型）时该项取中性 0.5，不影响上线

### 4.3 决策可解释

```
决策原因示例：
"[scored] 任务: reasoning(3)+tools(2) → 候选分数:
 openai/gpt-4o(0.82, 可靠性0.95), openai/gpt-4o-mini(0.61) → 链 [gpt-4o, gpt-4o-mini]"
```

- `rationale` 写入调用记录（`llm_call_log` 增 `decision_rationale` 字段，复用大模型调用记录方案）
- 管理 API 可查最近决策原因，便于人工校准规则/权重

## 5. 组件设计（`com.cosy.agent.agent.router` 包）

| 组件 | 职责 |
|---|---|
| `RouteDecisionProvider`（接口） | `RouteDecision decide(RouteContext ctx)`；可插拔 |
| `StaticChainResolver` | L0：现有 `resolveCandidates` 逻辑（默认实现） |
| `TaskTagResolver` | L1：特征提取 → 标签 → 链（规则表配置化） |
| `ScoringResolver` | L2：画像打分排序（委托 TaskTagResolver 选链后打分；指定模型/显式 routeType 直接放行） |
| `AutoRouter`（编排） | auto 模式入口：组装 RouteContext → 决策器链（Scoring→TaskTag→Static 回退）→ 返回有序候选 |
| `LlmCallStatsProvider` | 读取 `llm_call_log` 近 7d 统计（成功率/P95/降级率，按模型），L2 数据源；无记录返回空 |

**ModelRouter 改造点（最小）**：

```
call(prompt, modelChoice, routeType):
  modelChoice != auto → 现有单候选路径（不变）
  auto + routeType 显式 → 现有静态链路径（不变，显式类型优先）
  auto（无显式类型）→ AutoRouter.decide(ctx) → 有序候选 → 现有降级循环（不变）
```

- 降级循环、容错、Mock 短路、不可降级异常判定全部复用现有代码
- `AutoRouter` 未装配（开关关）时 auto 走 `StaticChainResolver` = 现状

## 6. 配置与管理 API

### 6.1 新增配置段（`cosy.agent.model-routing`）

```yaml
cosy:
  agent:
    model-routing:
      auto-resolver: static        # static | task-tag | scoring（默认 static=现状）
      auto-rules:                  # L1 规则表（热更新）
        - tag: tool-heavy
          condition: tools >= 3
        - tag: long-context
          condition: estTokens > 0.6 * contextWindow
        ...
      scoring-weights: { reasoning: 0.3, tools: 0.2, context: 0.2, reliability: 0.15, speed: 0.1, price: 0.05 }
```

- `auto-resolver` 三个档位即时切换（热更新），生产可灰度（先 static → task-tag → scoring）
- 规则表 / 权重均为结构化配置，管理 API `GET/PUT /api/agent/model-routing` 一并管理（v2.0 已有端点扩展）

### 6.2 客户端

**交互零变化**：Auto 默认 + 手动指定（下拉）。决策全部在后端。

可选增强（设置页只读）：
- "路由策略"卡片：当前 `auto-resolver` 档位 + 最近 N 条决策原因（调 `GET /llm-logs?decision=true`）

## 7. 与调用记录联动（闭环）

```
每次 auto 调用 ──► llm_call_log 记录:
                    决策原因(decision_rationale) · 候选链 · 实际命中 · 耗时 · 成功/降级
                            │ 近7d 聚合
                            ▼
                    LlmCallStatsProvider（成功率/P95/降级率 按模型）
                            │
                            ▼
                    ScoringResolver.reliability(c)  ← 数据越用越准
```

- 决策原因、候选链快照随记录落库 → 事后可审计"当时为什么选它"
- L3（远期）：调用记录 → 训练路由分类器（有监督：任务特征 → 哪个模型成功），替换启发式

## 8. 兼容与回退

| 项 | 决策 |
|---|---|
| 默认行为 | `auto-resolver=static`，与 v2.0 完全一致，零行为变化 |
| 决策器异常 | try/catch 回退 static，主请求不受影响 |
| 显式 routeType | 优先于决策器（用户/编排明确指定时不覆盖） |
| 指定模型 | 绕过决策器（单候选，现状） |
| 数据缺失 | 可靠性取 0.5 中性值；规则表缺标签回退 default 链 |
| 配置兼容 | 新增字段带默认值；旧 YAML/PUT 体不传即默认，不破坏 |

## 9. 实施步骤

| 步骤 | 内容 | 验收 |
|---|---|---|
| 1 | `RouteDecisionProvider` 接口 + `StaticChainResolver`（现状迁移）+ `AutoRouter` 编排 + 配置段 | 开关 static 时行为与 v2.0 完全一致（回归测试） |
| 2 | `TaskTagResolver`（L1）：特征提取 + 规则表配置化 + 标签链回退 | 单测：工具密集→tool-heavy 链；长上下文→long-context 链；未命中→default |
| 3 | ModelSpec 画像字段扩展（speed/reasoning/tool-support/price-tier）+ 管理 API 编辑 | 模型管理平台化 CRUD 扩展字段读写/打码正常 |
| 4 | `LlmCallStatsProvider`（读 llm_call_log 近 7d 统计）+ `ScoringResolver`（L2 打分排序） | 单测：分数排序正确、无数据中性值、稳定排序 |
| 5 | `llm_call_log` 增 `decision_rationale` 字段；ModelRouter 集成 AutoRouter（最小改造） | 端到端：auto 请求产生决策原因并落库 |
| 6 | 配置热更新验证（static→task-tag→scoring 切换即时生效） | 集成测试 |
| 7 | 客户端设置页"路由策略"只读卡片（可选） | 启动不报错 |
| 8 | 全量回归（后端 117+ tests / flutter analyze）+ 推送 | BUILD SUCCESS / 0 issues |

## 10. 演进项（远期，不在本期）

- **L3 LLM Router**：小模型决策 + 调用记录回流训练；决策结果可人工覆写（feedback 通道）
- **会话级画像**：per-session 模型偏好记忆（用户手动指定过的模型 → 该会话 auto 加权）
- **窗口感知防截断**：超窗口时自动拆分/摘要（与 long-context 链联动）
- **A/B 灰度**：决策器按会话比例灰度（static vs scoring 对比成功率）
